Frontend deployment: Vercel. Backend deployment: Render.
Axiom solves a precise, real problem: organizations need private, hierarchical, real-time internal communication that they fully own and control. Unlike public tools, Axiom enforces a strict power structure — not every user holds equal authority. The platform must be:
Instant — messages delivered under 100ms to all connected clients in the same room
Hierarchical — three global roles (superadmin, moderator, member) plus room-local roles, enforced server-side on every action
Extensible — slash commands execute real server-side actions, not cosmetic responses
Auditable — every administrative action is written to both Postgres and the Polygon Amoy blockchain, making the audit trail tamper-proof and publicly verifiable
Cryptographically secure — passwords hashed bcrypt rounds 12, JWT signed HMAC-SHA256, direct messages end-to-end encrypted with NaCl box

Section 2 — Why Blockchain is Load-Bearing
The audit log is written to Polygon Amoy testnet. This is architectural, not decorative. Here is exactly why:
The Problem With Postgres-Only Audit Logs
If admin action records live only in Postgres, any database administrator can silently delete them with DELETE FROM audit_log. There is no cryptographic proof an event occurred. The log is mutable. For a platform claiming tamper-proof accountability, this is architecturally dishonest.
What Polygon Amoy Provides
Immutability — once confirmed, no one can delete or alter the record, including the contract deployer
Public verifiability — any person with a tx hash can open amoy.polygonscan.com and read the event
Independent timestamp — block.timestamp is set by the network, not by your server clock
Demo moment — judges can verify on-chain events live during the presentation
Exactly Which Events Go On-Chain
On-chain (admin actions — low frequency, high accountability):
ROLE_CHANGE — when a user's global role is changed
KICK — when a user is removed from a room
BAN — when a user is banned from the platform
ROOM_ARCHIVED — when a room is archived
ROOM_CREATED — when a moderator or superadmin creates a room
Off-chain only — too frequent, gas cost is unreasonable:
message:sent — thousands per hour
room:joined — routine, non-destructive
room:left — routine, non-destructive
The blockchain is NOT used for storing messages. NOT used as a database. NOT used for payments. It is used exclusively for making admin actions permanently verifiable. Never write a message send event to the blockchain.

Section 3 — Why Cryptography is Load-Bearing
1. Password Hashing — bcrypt rounds 12
The server never stores plaintext passwords. Every password hashed with bcrypt at cost factor 12. On login, bcrypt.compare() verifies without reversing. If the database leaks, passwords are not exposed.
2. JWT Signature — HMAC-SHA256
JWT access tokens carry userId, username, and role in the payload, signed with a 32-character server secret. If a user modifies their role claim, the signature becomes invalid. Auth middleware verifies the signature on every request before it reaches any route handler. Role is NEVER read from the request body — only from the decoded, verified JWT.
3. End-to-End Encrypted Direct Messages — NaCl Box
DMs between two users use nacl.box (X25519-XSalsa20-Poly1305). Each user has a keypair. The public key is stored in the DB. The private key is encrypted with a key derived from the user's password via scrypt and stored encrypted in the DB.
Sender encrypts message client-side: nacl.box(message, nonce, recipientPublicKey, senderSecretKey)
Server receives only ciphertext + nonce — never the plaintext
Recipient decrypts client-side: nacl.box.open(ciphertext, nonce, senderPublicKey, mySecretKey)
Room messages are NOT E2EE — they are stored as plaintext for history. Only DMs are E2EE.

Section 6 — Complete Database Schema
Run every SQL statement in Supabase SQL editor in order. Do not modify column names — the backend references them directly.
Step 1: Users Table
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username TEXT UNIQUE NOT NULL,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'member'
    CHECK (role IN ('superadmin', 'moderator', 'member')),
  public_key TEXT,
  encrypted_private_key TEXT,
  key_salt TEXT,
  is_online BOOLEAN DEFAULT false,
  last_seen TIMESTAMPTZ DEFAULT NOW(),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  refresh_token TEXT
);
The superadmin is seeded on first boot from env vars. There is exactly one superadmin. Superadmin role cannot be assigned through the API — only through the seed script. The public_key, encrypted_private_key, and key_salt columns support E2EE direct messages.
Step 2: Rooms Table
CREATE TABLE rooms (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT UNIQUE NOT NULL
    CHECK (name ~ '^[a-z][a-z0-9-]{2,29}$'),
  description TEXT,
  is_private BOOLEAN DEFAULT false,
  created_by UUID REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  is_archived BOOLEAN DEFAULT false
);
Step 3: Room Members Table (Two-Tier Roles)
CREATE TABLE room_members (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  room_id UUID REFERENCES rooms(id) ON DELETE CASCADE,
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  local_role TEXT DEFAULT 'member'
    CHECK (local_role IN ('owner', 'moderator', 'member')),
  joined_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(room_id, user_id)
);
local_role is room-scoped. A global member can be the owner of their own room. Global role always takes precedence over local role when they conflict. Both tiers must be checked on every room action.
Step 4: Messages Table
CREATE TABLE messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  room_id UUID REFERENCES rooms(id) ON DELETE CASCADE,
  sender_id UUID REFERENCES users(id),
  content TEXT NOT NULL,
  is_command BOOLEAN DEFAULT false,
  is_system BOOLEAN DEFAULT false,
  edited_at TIMESTAMPTZ,
  deleted_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
Soft-delete only — set deleted_at, never hard delete. Client renders "[deleted]" for messages where deleted_at is not null.
Step 5: Direct Messages Table (E2EE — Ciphertext Only)
CREATE TABLE direct_messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sender_id UUID REFERENCES users(id),
  recipient_id UUID REFERENCES users(id),
  ciphertext TEXT NOT NULL,
  nonce TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
Step 6: Audit Log Table
CREATE TABLE audit_log (
  id BIGSERIAL PRIMARY KEY,
  event TEXT NOT NULL,
  actor_id UUID REFERENCES users(id),
  target_id UUID,
  room_id UUID,

  tx_hash TEXT,
  on_chain BOOLEAN DEFAULT false,

The audit_log table is APPEND-ONLY. There must be no DELETE or UPDATE routes for it. tx_hash is populated asynchronously after the blockchain write confirms.

7.3 Permission Middleware Code
File: backend/src/middleware/permission.middleware.ts
export const ROLE_WEIGHT = { member: 0, moderator: 1, superadmin: 2 };
export function requireRole(minGlobalRole: GlobalRole) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const user = req.user;
    if (!user) return res.status(401).json({ error: 'unauthorized', message: 'Authentication required' });
    if (ROLE_WEIGHT[user.role] < ROLE_WEIGHT[minGlobalRole]) {
      return res.status(403).json({ error: 'forbidden', message: 'Insufficient role' });
    }
    next();
  };
}
Role is ALWAYS read from the verified JWT (req.user.role) — never from the request body or query string. Client-side role checks are decorative only. The server re-checks on every single request and socket event.

8.2 Command Parser
File: backend/src/commands/parser.ts
export interface ParsedCommand { command: string; args: string[]; }
export function parseCommand(content: string): ParsedCommand | null {
  if (!content.startsWith('/')) return null;
  const [rawCmd, ...args] = content.slice(1).split(' ');
  return { command: rawCmd.toLowerCase(), args };
}

Section 10 — AuditLog Smart Contract
Already deployed at: 0xd9145CCE52D386f254917e481eB44e9943F39138 on Polygon Amoy. Keep a reference copy at contracts/AuditLog.sol.
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;
contract AuditLog {
    struct AuditEvent {
        string eventType;
        address actor;
        bytes32 actorId;
        bytes32 targetId;
        bytes32 dataHash;
        uint256 timestamp;
    }
    AuditEvent[] public events;
    address public owner;
    event AuditEventLogged(uint256 indexed index, string eventType,
        address indexed actor, bytes32 actorId, bytes32 targetId,
        bytes32 dataHash, uint256 timestamp);
    modifier onlyOwner() { require(msg.sender == owner, "Not authorized"); _; }
    constructor() { owner = msg.sender; }
    function logEvent(string calldata eventType, bytes32 actorId,
        bytes32 targetId, bytes32 dataHash) external onlyOwner {
        AuditEvent memory e = AuditEvent(eventType, msg.sender,
            actorId, targetId, dataHash, block.timestamp);
        events.push(e);
        emit AuditEventLogged(events.length-1, eventType,
            msg.sender, actorId, targetId, dataHash, block.timestamp);
    }
    function getEvent(uint256 i) external view returns (AuditEvent memory) {
        require(i < events.length, "Index out of bounds");
        return events[i];
    }
    function getEventCount() external view returns (uint256) {
        return events.length;
    }
}
