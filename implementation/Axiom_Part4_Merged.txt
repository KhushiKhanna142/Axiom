Section 45 — Security Checklist
Every item on this list must be implemented before deployment.
HTTP Security
Helmet.js enabled on all routes
CORS restricted to specific origins — no wildcard * in production
All cookies: httpOnly: true, secure: true (production), sameSite: strict
Rate limiting per user AND per IP — separate limiters for messages and commands
express-request-id — every request gets a unique ID for tracing
app.set("trust proxy", 1) — required for Render deployment and rate limiting
No sensitive data in URL query params
Authentication
Passwords hashed with bcrypt, rounds: 12 — never store plaintext
JWT secrets minimum 32 characters, randomly generated, different for access and refresh
Access tokens expire in 15 minutes
Refresh token rotation on every refresh — old token invalidated in DB
Refresh tokens in httpOnly cookies, never in localStorage
On logout: clear cookie AND invalidate refresh token in DB
Role Enforcement
Role is ALWAYS read from the verified JWT (req.user.role) — never from the request body
Server-side check on every Socket.io event — client-side role checks are decorative only
Superadmin role cannot be assigned via API — seed script only
Room membership verified on every message send and room action
Command permissions checked inside every command handler, not just at route level
Two-tier permission check: global role AND room-local role must both be satisfied
Input Validation
Every request body validated with Zod schema before any processing
Username: alphanumeric + underscores, 3-20 chars
Message content: max 4000 characters, stripped of null bytes, trimmed
Room names: lowercase alphanumeric + hyphens, 3-30 chars, must start with a letter
UUID format validated for all :id parameters
Parameterised queries only — never concatenate user input into SQL
Blockchain Key Security
Deployer private key stored in .env only — never committed to git
POLYGON_PRIVATE_KEY is testnet-only — no real ETH involved
.gitignore must include: .env, backend/.env, frontend/.env.local, node_modules, dist

Section 50 — Judge Q&A
Know these answers before you walk into the room. Do not read from notes.
Q: How do you enforce roles — couldn't a client fake their role?
A: The role lives in the JWT, which is signed with a secret key only the server knows. Even if a client modifies the token payload, the signature verification fails and the request is rejected with 401. Role is never read from the request body — only from the decoded, verified token. The exact same check runs on every Socket.io event via the auth middleware that attaches the user to socket.data on connection.
Q: Why blockchain for an internal messaging app?
A: Audit logs in Postgres are mutable — any database admin can run DELETE FROM audit_log. We use Polygon Amoy for admin actions because those are the events that need permanent accountability. Once a transaction is confirmed, no one can alter it, including us. Judges can open amoy.polygonscan.com right now and independently verify every admin action that happened during this demo. We don't use it for messages — only for low-frequency, high-stakes events.
Q: What happens if the Polygon RPC is down?
A: The circuit breaker opens after 3 failures in the 60-second window. The administrative action already succeeded before the blockchain write was attempted. The blockchain call is async, fire-and-forget. The tx_hash column in audit_log stays null until the chain recovers, at which point retries resume. The chat platform never goes down because of a blockchain issue. Users never see any degraded experience.
Q: How does the presence system work? What if the server crashes?
A: Presence is stored in Redis with a 30-second TTL. The client sends a heartbeat via Socket.io every 20 seconds, which refreshes the TTL. If the server crashes, no process refreshes the TTL. All presence keys expire naturally within 30 seconds and all users appear offline. On reconnect, the client re-authenticates and the server sets their presence key again. There is no stale "online" state that persists across crashes.
Q: What prevents someone from calling /promote via a raw API call?
A: The PATCH /api/users/:id/role endpoint has requireRole("superadmin") middleware applied at the router level, before the handler runs. Any JWT without the superadmin role gets a 403. The middleware is tested independently. It cannot be accidentally omitted — it wraps the entire route, not just the handler. Socket.io commands have the same check run inside the handler itself.
Q: What is the room-local role system for?
A: It lets a global member be the owner or moderator of their specific room. For example, a team lead who doesn't need platform-wide moderator powers can still manage their own team's room. Global role always takes precedence — a global moderator doesn't lose their platform-wide kick ability just because they're a local member somewhere. The two tiers are additive. Both must be satisfied on every room action.
Q: Can the system scale beyond one server?
A: Yes, with one addition: @socket.io/redis-adapter. Currently Socket.io events are scoped to one process. In a multi-instance deployment, the Redis adapter broadcasts events through Redis pub/sub to all server instances. Supabase and Upstash are already external services shared across any number of instances. The architecture is horizontally scalable — the adapter is a single import.
Q: How do commands avoid being a security risk?
A: Commands are parsed and executed entirely server-side. The client sends them as plain message strings starting with /. The server detects the prefix, routes to the command engine, and never broadcasts the raw command to the room — only the system message output. Every command handler checks the caller's role internally and throws if the actor lacks required permissions. A user cannot inject a command that bypasses permission checks because all checks live inside the server-side handlers.
Q: Why Supabase?
A: Three reasons: managed PostgreSQL with a connection pooler at the free tier, which matters for hackathon deployment. A useful real-time dashboard for inspecting the DB during the demo. And the JS client reduces boilerplate for standard queries while still supporting raw SQL for complex role checks. It is not a lock-in — the entire system works with any PostgreSQL-compatible database.
Section 51 — Final Implementation Notes
These are the details that separate a complete implementation from a half-finished one.
Every async function must have a try-catch. No unhandled promise rejections.
Every Socket.io event handler must be wrapped in try-catch and emit an error event on failure.
TypeScript strict mode enabled. No use of "any" type anywhere.
All database queries use parameterised inputs. Never concatenate user input into SQL.
The /api/health endpoint must NOT require authentication. Judges will test it first.
The audit_log table is append-only. There must be no DELETE or UPDATE routes for it.
The superadmin role can only be assigned via the seed script, never via the API.
Room names must be unique across the platform. Enforced with UNIQUE constraint + 409 response.
Message content must be sanitised: strip null bytes (\0), enforce max 4000 chars, trim whitespace.
Socket.io must work over HTTPS on Render. CORS config is inside the Server constructor.
Every role badge in the UI must come from the JWT payload — never from a client-side store that could drift.
The command autocomplete dropdown must only show commands the user has permission to execute.
Blockchain writes are always fire-and-forget. Never await them in a request handler.
Circuit breaker: 15s timeout, 50% error threshold, 60s reset window, 3 call volume minimum.
THE ONE THING THAT MUST NEVER HAPPEN: A plain member must never be able to perform a moderator or superadmin action. If you demo the platform and a member successfully kicks another user or promotes themselves, the demo is over. Test every role combination before the presentation, not during it. The role system is the puzzle. The judges are watching it specifically. Get it right.
